제7조(개인정보의 암호화) ① 개인정보처리자는 비밀번호, 생체인식정보 등 인증정보를 저장 또는 정보통신망을 통하여 송·수신하는 경우에 이를 안전한 암호 알고리즘으로 암호화해야 해요. 다만, 비밀번호를 저장하는 경우에는 복호화되지 아니하도록 일방향 암호화하여 저장해야 해요.안내서: 무작위 대입공격, 레인보우 테이블 공격 등에 대응하기 위한 조치를 하여야 하고, 그 수단으로 솔트값 추가를 고려할 필요가 있다.

알고리즘 선택

  • 안내서 예시 일방향 알고리즘: SHA-224/256/384/512 (국내·NIST·CRYPTREC·ECRYPT 공통 권고)
  • 사용 금지: MD5, SHA-1 등 보안강도가 낮은 것으로 판명된 알고리즘
  • 실무 권장: 솔트 + 반복 연산(키 스트레칭). PBKDF2-HMAC-SHA256, bcrypt, scrypt, Argon2 같은 비밀번호 전용 함수를 쓰면 무작위 대입 비용이 크게 올라가요.
  • API Access Key 같은 프로그램용 자격 증명은 이 기준의 “비밀번호”로 보지 않지만 저장 시 암호화 등 안전한 관리방안이 필요해요.

전송 구간 암호화 TLS

개인정보를 인터넷망 구간으로 송·수신할 때, 그리고 인증정보는 내부망을 포함한 모든 정보통신망에서 암호화해야 해요. 같은 로그인 요청을 HTTP와 HTTPS로 보내고, 중간 와이파이에 앉은 도청자가 무엇을 보는지 비교해 보세요.

보안서버 구축 점검

  • 개인정보 입력·조회 페이지 전체를 HTTPS로 제공 (로그인 폼만이 아니라 폼을 담은 페이지와 전송 대상 모두)
  • TLS 1.2 이상, 가능하면 TLS 1.3. SSL 2.0/3.0, TLS 1.0/1.1 비활성화
  • HTTP 접속은 HTTPS로 리다이렉트, HSTS 헤더 적용
  • 인증서 유효기간 만료 모니터링, 신뢰할 수 있는 인증기관 발급
  • 내부망 관리자 페이지·DB 접속도 인증정보는 암호화 전송 (제7조①)
  • API 통신(앱 ↔ 서버, 서버 ↔ 수탁사)도 TLS 적용
제7조 ④ 개인정보처리자는 개인정보를 정보통신망을 통하여 인터넷망 구간으로 송·수신하는 경우에는 이를 안전한 암호 알고리즘으로 암호화해야 해요.안내서: 보유한 개인정보의 수, 처리 환경 등을 고려하여 SSL 인증서, 응용 프로그램 등을 이용한 보안서버 등을 활용할 수 있다. ‘정보통신망’은 내부망과 외부망을 포함하므로 내부망에서 인증정보를 송·수신하는 경우에도 암호화해야 해요.

OWASP A03 InjectionⅢ-1

SQL 인젝션

사용자 입력을 문자열 이어붙이기로 쿼리에 넣으면, 입력 속 따옴표가 데이터의 끝을 선언하고 그 뒤가 SQL 코드로 해석돼요. 아래 가상 로그인 서버의 SQL 엔진은 브라우저 안에서만 돌아가요.

공격 과정 한눈에 보기

직접 입력해 보기

구동 원리

  1. 서버가 "... WHERE id = '" + id + "'"처럼 입력을 쿼리 문자열에 그대로 붙여요.
  2. 입력값의 '가 문자열 리터럴을 닫아 버려요.
  3. 이어지는 OR '1'='1은 항상 참인 조건이 되고, --는 뒤쪽 비밀번호 조건을 주석으로 지워요.
  4. DB는 조건을 만족하는 첫 행(대개 관리자)을 돌려주고, 서버는 로그인 성공으로 처리해요.

대응

  • PreparedStatement(바인딩 변수) 사용: 쿼리 구조와 데이터를 분리해 입력이 코드가 될 수 없게 함
  • ORM·쿼리 빌더의 파라미터 바인딩 사용, 동적 정렬 컬럼 등은 화이트리스트
  • DB 오류 메시지를 사용자에게 노출하지 않기 (오류 기반 정보 수집 차단)
  • DB 계정 최소 권한, 개인정보 컬럼 암호화(유출돼도 평문 노출 방지)
OWASP A03 InjectionⅢ-2

크로스사이트 스크립팅

게시판에 저장된 글을 HTML로 그대로 출력하면, 글에 섞인 태그와 이벤트 속성이 다른 사용자의 브라우저에서 실행돼요. 공격자는 피해자의 세션 쿠키나 화면의 개인정보를 가져갈 수 있어요.

유형

  • 저장형(Stored): 게시글·댓글에 저장되어 열람하는 모든 사용자에게 실행
  • 반사형(Reflected): 검색어 같은 URL 파라미터가 응답에 그대로 반사
  • DOM 기반: 클라이언트 스크립트가 innerHTML 등으로 입력을 그려 넣을 때

대응

  • 출력 위치에 맞는 인코딩: HTML 본문은 &lt; &gt; &quot; &#39; &amp; 변환
  • HTML 허용이 필요하면 검증된 라이브러리로 허용 태그만 남기는 화이트리스트 필터
  • 세션 쿠키에 HttpOnly, Secure, SameSite 속성
  • Content-Security-Policy로 인라인 스크립트 실행 제한
OWASP A01 Broken Access ControlⅢ-3

크로스사이트 요청 위조

브라우저는 요청을 누가 시작했든 해당 사이트의 쿠키를 자동으로 붙여 보내요. 서버가 “이 요청이 정말 우리 화면에서 나왔는지” 확인하지 않으면, 공격자 페이지가 피해자 대신 회원정보 변경을 실행해요.

대응

  • 상태를 바꾸는 요청(POST/PUT/DELETE)에 예측 불가능한 CSRF 토큰을 넣고 서버에서 세션 값과 대조
  • 세션 쿠키 SameSite=Lax 또는 Strict
  • 이메일·비밀번호·연락처 변경 등 중요 기능은 현재 비밀번호 재확인 또는 추가 인증
  • Origin/Referer 헤더 검증, GET 요청으로 상태 변경 금지
OWASP A04 Insecure DesignⅢ-4

파일 업로드 · 웹셸

서버가 실행할 수 있는 스크립트 파일(JSP, PHP, ASP 등)이 웹 루트 아래에 올라가면, 공격자는 그 주소를 호출하는 것만으로 서버에서 명령을 실행해요. 이것이 웹셸이고, DB 계정 정보를 읽어 개인정보를 통째로 빼 가는 대형 유출의 단골 경로예요.

대응

  • 허용 확장자 화이트리스트(jpg, png, pdf 등), 대소문자 정규화, 마지막 확장자 기준 판단
  • 파일 내용(매직 바이트)과 MIME 타입 확인, 크기 제한
  • 업로드 파일은 웹 루트 밖에 저장하고 다운로드는 별도 핸들러로 제공
  • 저장 파일명은 서버가 무작위로 생성, 업로드 디렉터리 스크립트 실행 권한 제거
  • 안내서 권고: 웹 취약점 점검 외에도 정기적으로 웹셸 등을 점검하고 조치
OWASP A01 Broken Access ControlⅢ-5

경로 조작 · 파일 다운로드

다운로드 기능이 파라미터로 받은 파일명을 그대로 경로에 붙이면, ../로 상위 디렉터리로 올라가 DB 접속 설정 같은 파일을 받아 갈 수 있어요.

대응

  • 파일명 대신 파일 ID를 받아 서버 측 매핑 테이블에서 실제 경로 조회
  • 경로를 정규화(canonicalize)한 뒤 허용된 기준 디렉터리로 시작하는지 확인
  • .., /, \, 인코딩된 변형(%2e%2e%2f) 차단
  • 설정 파일에 DB 비밀번호를 평문으로 두지 않기 (제7조⑥ 키·자격 증명 관리와 연결)
OWASP A01 Broken Access Control고시 제5조 · 제6조Ⅲ-6

접근통제 미흡

로그인은 확인하면서 “이 데이터가 이 사람 것인지”는 확인하지 않는 경우예요. 주소창의 회원번호를 하나 바꾸는 것만으로 다른 회원의 개인정보가 열려요. 실제 유출 사고에서 가장 흔한 유형 중 하나예요.

대응

  • 모든 요청에서 서버가 세션의 사용자와 요청 대상 데이터 소유자를 대조 (클라이언트 값 신뢰 금지)
  • 순차 번호 대신 추측하기 어려운 식별자 사용 (보조 수단일 뿐, 권한 검증을 대체하지 않음)
  • 화면에 필요한 항목만 응답, 마스킹 적용 (제12조 출력 최소화)
  • 짧은 시간에 다수 회원 조회 같은 이상 접근을 접속기록으로 탐지 (제6조①2, 제8조)
  • API도 동일하게 점검: 안내서는 API 권한 관리 미흡으로 인한 유출 증가를 경고해요

프롬프트 인젝션

2026년 안내서는 “AI 기술을 사용하여 개인정보를 처리하는 경우 프롬프트 인젝션 등 AI 취약점 공격이 발생할 수 있으므로 AI 보안 레드티밍 등을 통해 AI에 특화된 취약점 점검을 수행할 수 있다”고 안내해요. AI가 읽는 문서 속에 숨은 지시가 AI의 행동을 바꾸는 원리를 봐요.

대응

  • AI에게 주는 도구·데이터 권한 최소화 (고객 DB 전체 조회 권한 금지, 필요한 필드만)
  • 외부 문서·메일·웹페이지 내용은 “지시”가 아닌 “데이터”로 분리해 다루기
  • 개인정보 대량 출력, 외부 전송 같은 행동은 사람 승인 단계 추가
  • 출력 단계에서 주민번호·전화번호 패턴 탐지·마스킹
  • AI 보안 레드티밍으로 정기 점검, 결과 기록
웹셸고시 제6조③Ⅲ

웹셸 구동원리 — php2shell · node2shell

공격자가 서버가 ‘코드로 실행’하는 파일을 올리는 데 성공하면, 그 파일이 서버에서 명령을 수행하는 웹셸이 돼요. PHP 환경이면 php2shell, Node.js 환경이면 node2shell이라 불러요. 여기서는 공격 코드가 아니라 왜 생기고 어떻게 막는지 흐름만 봐요.

어떻게 셸이 되나(흐름) ① 게시판·첨부 등 업로드 지점 발견 → ② 확장자·MIME만 검사하는 허술한 검증 우회(예: 이미지로 위장) → ③ 업로드 파일이 웹에서 접근·실행 가능한 경로에 저장 → ④ 서버가 그 파일을 스크립트로 실행 → ⑤ 외부 입력을 받아 서버 명령·파일 접근 수행(=셸). 핵심 원인은 ‘실행될 수 있는 위치에, 실행될 수 있는 형식으로 저장’되는 것.공공: 홈페이지 게시판 첨부가 흔한 통로 — 고시 제6조③ 관리자페이지·취급 개인정보 노출 방지

막는 법(방어)

  • 내용 기반 화이트리스트 검증 — 확장자·MIME만 믿지 말고 실제 포맷(매직넘버) 확인, 허용 형식만 통과
  • 업로드물은 웹루트 밖에 저장하고, 다운로드는 중계 스크립트로만 — 직접 URL 접근·실행 차단
  • 업로드 디렉터리에서 스크립트 실행 비활성화(예: 해당 경로 실행권한 제거, 정적 파일로만 서빙)
  • 파일명 난수화, 이미지 재인코딩(내장 코드 제거), 크기·개수 제한
  • WAF·백신 연동, 업로드/다운로드 로그 기록과 이상징후 점검
  • 최소권한 실행 계정(웹 프로세스가 시스템 전체 권한을 갖지 않게)
Zero-dayⅢ

제로데이(0-day) 취약점

아직 패치가 없는(공개·수정 전) 취약점을 노리는 공격이에요. 개발자가 문제를 안 지 ‘0일’, 즉 고칠 시간이 없었다는 뜻이에요. 백신·패치로 못 막을 수 있어 특히 위험해요. 완벽히 예방은 어려워도 피해를 줄이는 구조를 갖추는 게 핵심이에요.

왜 위험한가 알려진 취약점은 패치로 막지만, 제로데이는 대응 수단 자체가 아직 없음. 그래서 ‘막기’보다 터져도 덜 번지게 하는 다층 방어와 빠른 탐지·대응이 중요해요.최근 공공부문 사고도 상당수는 기본 수칙·패치 관리 미흡에서 비롯 — 노후 SW 교체가 중요

피해를 줄이는 법

  • 신속한 패치 관리 — 공개 즉시 적용하는 프로세스(제로데이가 1-day가 되기 전에)
  • 가상 패치(WAF 규칙)로 패치 전 임시 차단
  • 최소권한·망 분리·세분화로 침해 시 확산 차단(한 곳이 뚫려도 전체로 못 번지게)
  • 이상행위 탐지(EDR·IDS)와 접속기록 점검으로 조기 발견
  • 중요 데이터 백업·복구 체계(랜섬·파괴 대비), 노후·단종 SW 교체
  • 위협 인텔리전스 공유(기관·업계)로 조기 경보 수신
정찰안전성 기준 제6조Ⅲ

포트 스캐닝 — 공격 전 ‘정찰’

건물에 침입하기 전 열린 문·창문을 살피듯, 공격자는 서버의 어떤 포트(문)가 열려 있고 어떤 서비스가 도는지 먼저 훑어봐요. 이 정찰(스캐닝)로 약점을 고른 뒤 공격이 이어지죠. 열린 문을 줄이고, 두드리는 걸 알아채는 게 방어의 출발이에요.

개념 포트는 서비스가 드나드는 ‘문’(예: 웹 80·443, 원격 22·3389 등). 스캐닝은 어떤 문이 열려 있는지 확인하는 탐지 행위로, 그 자체가 공격 직전 단계예요. 열려 있지만 쓰지 않는 문, 낡은 서비스가 노출되면 침입 통로가 돼요.접근통제(제6조): 접속 IP 제한·탐지, 불필요 서비스 차단으로 비인가 접근 통제
⚡ AI가 바꾸는 판도: 최근 공격자는 AI 도구로 취약점 탐색·정찰을 사람보다 훨씬 빠르게 자동화해요(한 사례는 네트워크 깊숙이 침투까지 약 15분). 영국 NCSC는 “구식·미패치 방어는 AI 시대에 더 위험하다”고 경고했어요. → 신속 패치·자동 탐지·최소 노출이 그만큼 더 중요해졌어요.

막는 법(방어)

  • 불필요한 포트·서비스 폐쇄 — 안 쓰는 문은 잠그기(최소 노출 원칙)
  • 방화벽으로 허용 IP·포트만 열고, 관리용 포트(원격접속)는 외부 직접 노출 금지
  • IDS/IPS로 스캔 트래픽 탐지·차단, 반복 접속 IP 자동 차단
  • 외부 관리 접속은 VPN·2단계 인증을 거쳐서만
  • 서비스 배너·버전 정보 최소화로 식별 단서 줄이기
  • 정기 취약점 점검·모의해킹으로 내가 먼저 열린 문 찾기(2027.1 공공시스템 점검·침투테스트 의무화)

AI 보안 프레임워크 — Agentic Top 10 · NIST AI RMF

스스로 판단해 도구를 쓰고 행동하는 에이전트형 AI(Agentic AI)가 공공·업무에 들어오면 새로운 위험이 생겨요. 국제 표준 두 가지로 큰 그림을 잡아요 — 위협 목록 OWASP Agentic Top 10, 그리고 위험관리 체계 NIST AI RMF.

OWASP Top 10 for Agentic Applications (ASI01–10, 2026)

ASI01 · 목표 탈취Agent Goal Hijack — 숨은 지시로 에이전트의 목표를 바꿔 악용🛡 지시·목표의 출처 검증, 외부 콘텐츠는 ‘데이터’로 분리

ASI03 · 신원·권한 남용Identity & Privilege Abuse — 과도한 권한·위임 토큰 악용🛡 최소권한·NHI 관리·토큰 범위 제한

ASI08 · 연쇄 실패Cascading Failures — 한 에이전트 오류가 전체로 전파🛡 서킷브레이커·격리·한도 설정
ASI09 · 인간-에이전트 신뢰 악용Human-Agent Trust Exploitation — 과신을 노려 사용자를 속임🛡 행동 투명성·확인 단계·설명 제공
ASI10 · 통제 벗어난 에이전트Rogue Agents — 의도를 벗어나 자율 행동🛡 모니터링·킬스위치·권한 경계

개인정보 유출 대응

예방이 전부는 아니에요. 유출이 실제로 일어났을 때 무엇을, 언제까지, 누구에게 해야 하는지가 피해 규모를 갈라요. 인지 → 피해 최소화 → 72시간 내 통지·신고 → 피해 구제·재발 방지의 순서를 따라가요. 근거: 「개인정보 유출등 대응 안내서」(2026.9.).

제34조(개인정보 유출등의 통지·신고) ① 개인정보처리자는 개인정보가 분실·도난·유출(이하 “유출등”)되었음을 알게 되었을 때에는 정당한 사유가 없으면 72시간 이내에 다음 각 호의 사항을 해당 정보주체에게 알려야 한다.
1. 유출등이 된 개인정보의 항목 2. 유출등이 된 시점과 그 경위 3. 피해를 최소화하기 위하여 정보주체가 할 수 있는 방법 등에 관한 정보 4. 개인정보처리자의 대응조치 및 피해 구제절차 5. 피해를 신고·상담할 수 있는 부서 및 연락처
③ 개인정보처리자는 유출등의 규모, 민감성 등 대통령령으로 정하는 경우에는 72시간 이내에 보호위원회 또는 전문기관에 신고해야 해요.개인정보 유출신고 시스템: brss.pipc.go.kr · 개인정보침해신고센터 118
